VC SCM Studio — quick guide

This is a static SCM editor for Grand Theft Auto: Vice City (PC). Everything runs in your browser — no server. Open main.scm from your game folder (or use the bundled copy), edit the script, press Assemble, and save the new main.scm back. Always back up your original first.

1. Workflow

  1. Load: Open .scm reads a binary SCM and disassembles it into readable source, split into HEADER / MAIN / MISSION sections. Open source restores a previously saved source text, including your edits.
  2. Edit: pick a section, press Edit (or double-click the code), type, press Edit/Done or Esc to return to the readable view. Edited sections are marked with ● in the section navigator (behind the ☰ Sections button on phones).
  3. Assemble (or Ctrl+S): builds one binary from all sections. Errors appear in the problem list — click one to jump to the line.
  4. Save: Save .scm downloads the assembled game file; Save source downloads the text so you can keep working later.

2. The source language

The disassembler prints the widest-compatible subset of SCM assembly:

:LABEL_0001A4B0        // a jump target. GOSUB-safe if inside one section
0004: $8 0              // opcode 0004 (SET_VAR_INT), two operands
00D6: 0                 // conditions are plain opcodes, see below
004D: @LABEL_0001A4B0   // GOTO_IF_FALSE
0050: @LABEL_0001A5C0   // GOSUB
0051:                   // RETURN
0002: @LABEL_1 @LABEL_2 // jump table (mission select)
00BC: 'TEXT_KEY' 5000 1 // 8-char text label
03A4: 'MAIN'            // SCRIPT_NAME uses a text label too
0001: 250              // WAIT 250 ms
00A5: #LANDSTAL 0.0 0.0 0.0 $12 // model = integer, written with its map name
  • Comments start with // and run to end of line.
  • Globals are $8, $12… always multiples of 4. The assembler auto-sizes the globals block from the highest $N you use.
  • Locals are 0@ … 15@, plus timers 16@, 17@. Each script has its own locals.
  • Floats print rounded to the fewest decimals that still assemble to the exact same bytes (1999.92, 0.3, 100.0) — what you see is what the game gets, bit for bit.
  • Labels: define with :NAME, use with @NAME. Labels live inside one section — never jump between missions.
  • Opcodes may be written with or without the hex prefix: WAIT 0 and 0001: WAIT 0 both work. If both are given and disagree, the written prefix wins and produces an error pointing at the canonical opcode.
  • Conditions: 00D6 (ANDOR) opens a condition chain and 004D (GOTO_IF_FALSE) jumps when it fails; NOT before an instruction negates that check. These are ordinary opcodes in this view — keep every chain paired with its jump or the game will misbehave.

3. Variable names

Instead of raw $offsets, the code view shows a friendly name for every global: player_char, mission_flag, main_tick_ms. Names are color-coded by what the variable is — constant, entity handle, boolean flag, coordinate, and so on. Hover a name for its type, read/write counts and origin; use the Names button to switch back to raw offsets.

Click any name to rename it. Your names are stored in this browser only (export/import them as JSON from the rename dialog). Names are a display layer: the editor and assembler keep working with $offsets, so renaming can never break your build. A names ~ badge means the loaded file differs from the retail script the names were built from — most still apply, but treat them as approximate.

Your renames live in the browser's local storage. Export names (toolbar, or inside the rename dialog) downloads them as a small vcscm_names.json file: keep it as a backup, mail it to yourself, or copy it to another computer, then Import names there to get the same names back. The file remembers which game file the names were made for, and the editor tells you if you import it while a different file is loaded.

4. Opcodes view

Search the full 1,424-opcode database by name or hex id (e.g. 00D6). Clicking an opcode shows every argument with its type, description, enum and rules — then Insert drops a ready-made template line into your current section.

5. Structure view

Shows the real engine budgets from the binary: main-block size (limit 225,512 bytes on PC), largest mission (limit 35,000), mission count, object list and global usage. Bars turn red when a limit is exceeded — the game will not load such a file.

6. Editing aids

  • Autocomplete: while editing, just start typing and pick from the list (Tab/Enter accepts, ↑/↓ move, Esc dismisses, Ctrl+Space forces it open). After $ you get global offsets with their names, after @ the labels in this section, after # model names, anywhere else opcode names and keywords.
  • Signature hint: the toolbar shows the opcode on your line with every argument (hover for details). An unknown name gets a "did you mean ...?" suggestion instead.
  • Live check: a moment after you stop typing, problem lines are marked in the gutter — red for errors, yellow for warnings. Hover a mark for the message. Assemble is still the final word.
  • Label jump: click any @label in the code view to jump to its definition. Unknown opcode names are shown in red.
  • Snippets: the toolbar button inserts ready-made IF/ELSE, wait-loop, GOSUB, mission-start and named-global skeletons at the cursor.
  • Go to line: the toolbar box jumps straight to a line number.

7. Things to know

  • Mission order in the file decides the mission numbers — do not reorder or delete //== SECTION: MISSION n == headers.
  • The HEADER section holds the object list (DEFINE OBJECT) and the DEFINE MISSIONS count. Keep the count equal to the number of mission sections.
  • Text labels hold at most 7 visible characters plus the terminator; longer keys are truncated with a warning.
  • Optional/variadic arguments (e.g. extra GOTO targets, STRING_FORMAT args) are used as-is — match the count the original line had.
